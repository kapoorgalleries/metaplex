# Kit verification catches four silent-failure bugs

The Trimurti network kit under `ops/network/` is substantially correct against current official sources, but the verification pass found **four defects that would fail silently or endanger data**, about a dozen wrong facts, and a longer tail of wording gaps. The commands that matter most were right: the Claude Code, Codex and Gemini install lines, the Windows `Add-WindowsCapability` / `icacls` / `DefaultShell` sequence, the macOS `sshd_config.d` drop-in, and the Tailscale Linux installer all match vendor text verbatim. The silent failures were elsewhere: `update-all.ps1` called `Get-WindowsUpdate -Install` from an SSH session, which the Windows Update Agent rejects with `E_ACCESSDENIED` so **no OS update was ever installed while the script still exited 0**; `disk-triage.sh` read SMART raw values from `$NF` instead of column 10, so a drive with a `(0 1)` tail on its reallocated-sector line was **graded one step too healthy**; `hulk-drives.md` ran `hdparm --security-erase` without the mandatory `--security-set-pass NULL`, so the disposal wipe would not run; and its `mount -o ro` on ext4 **replays the journal and writes to a failing disk**. Two more items were wrong in a dangerous direction: `winget install --id tailscale.tailscale -e` matches nothing because `-e` is case-sensitive, and the NAS checklist's "~5 s for a safe shutdown" on Synology sits inside the 5–10 s forced-power-off range. The wrong-fact tier is dominated by the Windows Public-profile claim ("nothing inbound works": the kit's own SSH rule applies to every profile), the router DNS row (1.1.1.1 is unfiltered; Quad9 warns against mixing filtered and unfiltered resolvers), a "local hostnames in DNS" setting that does not exist on Netgear, TP-Link, eero or Google Nest, and small label errors (`"Login with Google"`, `claude doctor` as a login check, Codex "needs Node 20+"). As of commit `cccdb95` (2026-09-22) the kit already carries fixes for every tier-1 and tier-2 item; the remaining open items are wording additions listed in the table below. Roughly half of the primary vendor sites were unreachable through the session proxy, so the report marks which findings rest on search snippets rather than fetched pages.

## The three AI CLIs: commands were right, the login prose was not

### Codex CLI: npm still official, but OpenAI's headline route is now its own installer

The kit installed Codex with `npm install -g @openai/codex@latest` on all three OSes and described it as an npm package that "need[s] Node 20+" (`bootstrap-ai-clis.sh` lines 2–4 and 41; `.ps1` lines 2–5 and 37). The npm route remains officially listed, but the `openai/codex` README now leads with standalone installers, `curl -fsSL https://chatgpt.com/codex/install.sh | sh` on Mac/Linux and `powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"` on Windows, then lists npm and `brew install --cask codex` as "also" routes and raw GitHub binaries last ([openai/codex README](https://github.com/openai/codex/blob/main/README.md)). The npm package is only a launcher: `bin/codex.js` maps platform and architecture to a target triple and spawns a native binary from one of six platform packages, and its `engines` field is `"node": ">=16"`, so the kit's "Codex needs Node 20+" was a Gemini requirement mis-attributed to Codex ([npm registry](https://registry.npmjs.org/@openai/codex/latest)). The Homebrew formula no longer exists; `codex` is a cask at 0.155.1, and the migration issue records that `brew upgrade codex` was reported outdated in favour of `brew upgrade --cask codex` ([homebrew-cask codex.rb](https://github.com/Homebrew/homebrew-cask/blob/master/Casks/c/codex.rb); [openai/codex issue #5317](https://github.com/openai/codex/issues/5317)). The installer defaults are `~/.local/bin` (already on the kit's PATH for Claude Code) and `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin`, with `CODEX_NON_INTERACTIVE=1` to suppress prompts and SHA-256 digest checks ([scripts/install/install.sh](https://github.com/openai/codex/blob/main/scripts/install/install.sh); [scripts/install/install.ps1](https://github.com/openai/codex/blob/main/scripts/install/install.ps1)).

Windows native is now a first-class target: npm publishes `@openai/codex-win32-x64` and `-win32-arm64`, and the official Windows page (reachable only as a snippet) says "Use the native Windows sandbox by default" with `[windows] sandbox = "elevated"` as the preferred mode, choosing WSL only for Linux-native tooling ([developers.openai.com/codex/windows](https://developers.openai.com/codex/windows), snippet). The repo's `docs/install.md` still says "Windows 11 via WSL2", which is stale text in a build-from-source guide ([docs/install.md](https://github.com/openai/codex/blob/main/docs/install.md)). OpenAI's own November 2025 announcement called the sandbox "highly experimental" and no later official "stable" statement was found ([discussion #6065](https://github.com/openai/codex/discussions/6065)), so the kit's native-Windows choice is right but deserves a one-line sandbox caveat.

The login routes were verified by running `@openai/codex@0.155.1` locally: `codex login --help` documents exactly the flags the kit uses, `--with-api-key` (stdin), `--with-access-token`, `--device-auth` and `codex login status`; with `OPENAI_API_KEY` or `CODEX_API_KEY` exported but no login, `codex login status` prints "Not logged in" and exits 1, while `printf 'sk-...' | codex login --with-api-key` writes `$CODEX_HOME/auth.json` with mode 0600 and `login status` then exits 0 ([npm registry package](https://registry.npmjs.org/@openai/codex/latest)). Two prerequisites the kit omitted: device-code login "need[s] to [be] enable[d] ... in your ChatGPT security settings (personal account) or ChatGPT workspace permissions" ([developers.openai.com/codex/auth](https://developers.openai.com/codex/auth), snippet), and the browser flow works over SSH if you forward the callback with `ssh -L 1455:localhost:1455 <host>`, after which `auth.json` "is not tied to a specific host" and can be copied to another machine ([docs/authentication.md @ rust-v0.42.0](https://github.com/openai/codex/blob/rust-v0.42.0/docs/authentication.md)). Credential storage is configurable through `cli_auth_credentials_store` (`file` default, `keyring`, `auto`, `ephemeral`) ([codex-rs/config/src/types.rs](https://github.com/openai/codex/blob/main/codex-rs/config/src/types.rs)). The README's plan list ("Plus, Pro, Business, Edu, or Enterprise") is narrower than the help-centre article, which adds Free and Go ([help.openai.com article 11369540](https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan), snippet). For updates, `codex update` is a built-in universal updater whose `UpdateAction` enum covers npm, bun, pnpm, vp, `brew upgrade codex` and both standalone installers; on the sandbox's npm install it printed "Updating Codex via `npm install -g @openai/codex`..." and exited 0 without prompting ([codex-rs/tui/src/update_action.rs](https://github.com/openai/codex/blob/main/codex-rs/tui/src/update_action.rs)). **Correction applied (`cccdb95`)**: the bootstrap scripts now use the official installer with npm as fallback, the Node log line attributes 20+ to Gemini only, `update-all` calls `codex update`, and the sign-in block carries the device-code prerequisite, the port-forward alternative, the `auth.json` path and the "exporting the variable alone is not a login" warning. **Still open**: the Windows sandbox caveat and the Free/Go plan note are optional additions.

### Gemini CLI: the install was exactly right, the menu label was not

The kit's `npm install -g @google/gemini-cli@latest` is the method the docs call "standard", with Homebrew and MacPorts as official alternatives and `npx` filed under "advanced"; the runtime floor is "Node.js 20.0.0+" and the package's `engines` is `>=20`, so the kit's `-ge 20` checks and Node 22 install are correct ([docs/get-started/installation.mdx](https://github.com/google-gemini/gemini-cli/blob/main/docs/get-started/installation.mdx); [npm registry](https://registry.npmjs.org/@google/gemini-cli/latest)). The label was wrong: the docs and the shipped 0.60.0 bundle both say **"Sign in with Google"**, not the kit's "Login with Google" ([docs/get-started/authentication.mdx](https://github.com/google-gemini/gemini-cli/blob/main/docs/get-started/authentication.mdx)). More consequential for this fleet, the auth table says organisation users "with a company, school, or Google Workspace account" must set `GOOGLE_CLOUD_PROJECT` before signing in, and the troubleshooting page gives the symptom without it, "Failed to sign in. Message: Request contains an invalid argument", and the opposite symptom for a personal account that sets it, the "named user on your organization's Gemini Code Assist Standard edition" error ([authentication.mdx](https://github.com/google-gemini/gemini-cli/blob/main/docs/get-started/authentication.mdx); [troubleshooting.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/troubleshooting.md)). The operator's sign-in address is on a custom domain, so this line matters more here than usual.

`NO_BROWSER=true gemini` does what the kit says but is documented nowhere on the docs site: the source reads `process.env['NO_BROWSER']`, prints "Please visit the following URL to authorize the application:" and prompts "Enter the authorization code: " with a five-minute timeout, and throws "Manual authorization is required but the current session is non-interactive" if there is no TTY, which means the login cannot be pushed through `run-remote.sh` and needs `ssh -t` ([oauth2.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/code_assist/oauth2.ts)). Over SSH the browser is suppressed automatically anyway (`SSH_CONNECTION` on non-Linux, no `DISPLAY` on Linux) ([browser.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/utils/browser.ts)). The persisted choice lives in `~/.gemini/settings.json` as `security.auth.selectedType` with values `oauth-personal`, `gemini-api-key`, `vertex-ai` (plus `cloud-shell`, `compute-default-credentials`, `gateway`) ([configuration.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/configuration.md); [contentGenerator.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/core/contentGenerator.ts)), and OAuth tokens sit in the OS keychain under service `gemini-cli-oauth` with `~/.gemini/oauth_creds.json` as the legacy fallback ([oauth-credential-storage.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/code_assist/oauth-credential-storage.ts)). Do not adopt `gemini update`: the cheatsheet lists it, but the 0.60.0 bundle registers no such command and the feature request was "Closed as not planned" ([issue #18618](https://github.com/google-gemini/gemini-cli/issues/18618)); the CLI instead self-updates on launch (`general.enableAutoUpdate`, default `true`) by spawning the package manager's own command ([handleAutoUpdate.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/cli/src/utils/handleAutoUpdate.ts)). On quota, the docs' table gives **1,000 requests/day** for Google sign-in and **250/day, Flash only** for an unpaid API key, but the README claims 1,000/day for the API key, so the API-key figure is unsettled ([quota-and-pricing.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/resources/quota-and-pricing.md)). **Correction applied**: label, Workspace rule, API-key URL and the auto-update sentence in README. **Still open (optional)**: credential locations, `/auth`, `/stats model` and the quota comparison.

### Claude Code: install and SSH text correct; `claude doctor` was the wrong login check

Both kit install commands are the documented native installer, `curl -fsSL https://claude.ai/install.sh | bash` and `irm https://claude.ai/install.ps1 | iex` (the kit's `Invoke-Expression (Invoke-RestMethod ...)` is the un-aliased form), and "Native installations automatically update in the background" confirms the kit's auto-update claim; Homebrew (`claude-code` stable, `claude-code@latest`), WinGet (`Anthropic.ClaudeCode`) and apt/dnf/apk exist but do not auto-update by default ([Setup](https://code.claude.com/docs/en/setup)). The TLS 1.2 line the `.ps1` sets is the documented fix for installer TLS errors ([Troubleshoot installation](https://code.claude.com/docs/en/troubleshoot-install)). Install locations match the kit's PATH assumptions, `~/.local/bin/claude` as a symlink into `~/.local/share/claude/versions/` and `%USERPROFILE%\.local\bin\claude.exe`, but the docs never promise PATH persistence and their error table anticipates "PowerShell installer completes but `claude` is not found", giving the `[Environment]::SetEnvironmentVariable('PATH', "$currentPath;$env:USERPROFILE\.local\bin", 'User')` fix ([Troubleshoot installation](https://code.claude.com/docs/en/troubleshoot-install)). The `.ps1` did not persist that directory and `verify.sh`'s Windows probe did not prepend it; both are now fixed (`bootstrap-ai-clis.ps1` line 47, `verify.sh` line 22).

The README's "Check: `claude doctor`" under the sign-in bullet was wrong: `claude doctor` "prints read-only installation and settings diagnostics", while **`claude auth status` exits 0 if logged in, 1 if not** and `--text` gives readable output ([CLI reference](https://code.claude.com/docs/en/cli-reference)). The kit's SSH prose ("press `c` to copy the URL ... 'Paste code here if prompted'") matches the docs verbatim, and `claude auth login` is the documented fallback that "reads the pasted code from standard input" when the interactive paste fails ([Authentication](https://code.claude.com/docs/en/authentication); [Troubleshoot installation](https://code.claude.com/docs/en/troubleshoot-install)). The `setup-token` bullet needed three fixes: the command "opens the same browser authorization flow as `/login`" (it needs a browser, not "a machine that is already signed in"), it requires "a Pro, Max, Team, or Enterprise plan" (the kit omitted Enterprise), and the token "can only make model requests, so it can't establish Remote Control sessions or fetch claude.ai connectors" and is read again in every new session until unset ([Authentication](https://code.claude.com/docs/en/authentication)). Two fleet facts the kit lacked: on macOS "when the Keychain rejects the write, such as when it's locked in an SSH session, Claude Code stores your login in `~/.claude/.credentials.json` with file mode `0600`", the same storage as Linux, recoverable with `security unlock-keychain ~/Library/Keychains/login.keychain-db` then `/logout` and `/login`; and an exported `ANTHROPIC_API_KEY`, once approved, overrides the subscription and can produce "This organization has been disabled" errors ([Authentication](https://code.claude.com/docs/en/authentication); [Troubleshoot installation](https://code.claude.com/docs/en/troubleshoot-install)). Requirements are macOS 13+, Windows 10 1809+, Ubuntu 20.04+/Debian 10+, 4 GB RAM and a 64-bit CPU with AVX ("roughly pre-2013" processors fail with `Illegal instruction`, no workaround) ([Setup](https://code.claude.com/docs/en/setup); [Troubleshoot installation](https://code.claude.com/docs/en/troubleshoot-install)). Support articles (snippets only) say one Pro/Max subscription covers every device with the same login and that all surfaces "count towards the same usage limit" ([Use Claude Code with your Pro or Max plan](https://support.claude.com/en/articles/11145838-use-claude-code-with-your-pro-or-max-plan), snippet); no document states a device cap. **Correction applied**: README line 88 now uses `claude auth status`, the corrected `setup-token` text, the Keychain-over-SSH note and the shared-pool sentence. **Still open**: the `ANTHROPIC_API_KEY` warning and an AVX pre-check are additions.

## SSH servers: Windows commands match Microsoft verbatim, the Public-profile claim did not

### Windows 10/11 OpenSSH Server (research question 4)

Every command in `enable-ssh-server.ps1` is character-for-character Microsoft's: `Add-WindowsCapability -Online -Name OpenSSH.Client~~~~0.0.1.0` / `OpenSSH.Server~~~~0.0.1.0`, `Start-Service sshd`, `Set-Service -Name sshd -StartupType 'Automatic'`, and the in-box Feature on Demand is "the recommended option for most users" because Microsoft "supports and services this version through Windows Update" ([Get started with OpenSSH for Windows](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_install_firstuse), ms.date 09/04/2025, read from the `MicrosoftDocs/windowsserverdocs` source). The firewall rule is likewise Microsoft's exact text, and the page states installing the server "creates and enables a firewall rule named `OpenSSH-Server-In-TCP`" while still asking you to verify and create it if missing ([same](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_install_firstuse)). The admin-key handling is right: "If the user belongs to the administrator group, `%programdata%/ssh/administrators_authorized_keys` is used instead", the file "must only have permission entries for the `NT Authority\SYSTEM` account and `BUILTIN\Administrators`", and the documented command is `icacls.exe "C:\ProgramData\ssh\administrators_authorized_keys" /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"` ([OpenSSH Server configuration](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-server-configuration); [Key-based authentication](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement)). The behaviour comes from the `Match Group administrators` block at the end of the default `sshd_config` ([openssh-portable sshd_config](https://github.com/PowerShell/openssh-portable/blob/latestw_all/contrib/win32/openssh/sshd_config)). Microsoft recommends SID form (`*S-1-5-32-544`) for non-English Windows, an optional robustness change. `DefaultShell` as a `String` value under `HKLM:\SOFTWARE\OpenSSH` set with `New-ItemProperty ... -PropertyType String -Force` is Microsoft's own example; `DefaultShellCommandOption` defaults to `-c`, which `powershell.exe` and `pwsh.exe` accept, so the kit is right not to set it ([OpenSSH Server configuration](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-server-configuration); [Win32-OpenSSH wiki: DefaultShell](https://github.com/PowerShell/Win32-OpenSSH/wiki/DefaultShell)).

The network-profile wording was the error. The kit said "Inbound rules only apply on Private/Domain networks; a Public profile blocks SSH, SMB and ping" (`enable-ssh-server.ps1` line 35), "Windows blocks inbound ping, SSH and SMB on Public" (`netscan.ps1` line 36) and "nothing inbound works" (README item 2). Microsoft's description of Public is "Your PC is hidden from other devices on the network and can't be used for printer and file sharing" ([Get-NetConnectionProfile](https://learn.microsoft.com/en-us/powershell/module/netconnection/get-netconnectionprofile)), and because neither Microsoft's nor the kit's `New-NetFirewallRule` passes `-Profile`, whose "default value is Any", **the kit's own SSH rule admits SSH on Public networks** ([New-NetFirewallRule](https://learn.microsoft.com/en-us/powershell/module/netsecurity/new-netfirewallrule)). `Set-NetConnectionProfile -InterfaceIndex <n> -NetworkCategory Private` is the documented cmdlet ([Set-NetConnectionProfile](https://learn.microsoft.com/en-us/powershell/module/netconnection/set-netconnectionprofile)). The kit's claim that an Administrators-group SSH session is elevated is supported by primary evidence but not by any Microsoft page: the maintainers closed "SSH login has full admin rights and there's no way to not grand them" as Resolution - Answered ([Win32-OpenSSH #1652](https://github.com/PowerShell/Win32-OpenSSH/issues/1652)), and the token is created by an S4U/network logon in `win32_usertoken_utils.c`, which is why Windows Update, DPAPI and outbound credential use still refuse it ([openssh-portable win32_usertoken_utils.c](https://github.com/PowerShell/openssh-portable/blob/latestw_all/contrib/win32/win32compat/win32_usertoken_utils.c)); Microsoft states that "a remote session opened via key-based authentication doesn't have associated user credentials" ([Key-based authentication](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement)). Two additions: key-based auth does not work for Microsoft Entra ID accounts ("Microsoft Entra ID accounts don't support key-based authentication"), and file-based sshd logging needs `SyslogFacility LOCAL0` (default AUTH goes to ETW) ([OpenSSH Server configuration](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-server-configuration)). **Correction applied**: the Public-profile wording in all three files and README item 8 ("What a Windows SSH session can and cannot do"). **Still open**: the Entra ID line, the `Match Group` alternative, the SID-form `icacls`, and the unverified `OpenSSH/Operational` log name in README item 7.

### macOS Remote Login, Full Disk Access and `sshd_config.d` (research question 5)

`systemsetup -setremotelogin on` still works on Sonoma, Sequoia and Tahoe only when the calling terminal has Full Disk Access; Apple's note is "first give the parent process full-disk-access" ([Apple Support 101653](https://support.apple.com/en-us/101653), snippet) and the exact failure text, reproduced on macOS 15.7.3 in September 2026, is `setremotelogin: Turning Remote Login on or off requires Full Disk Access privileges.`, with the twist that a tmux server started before the grant keeps the old denial ([alehatsman/dotfiles issue #4](https://github.com/alehatsman/dotfiles/issues/4)). The kit discarded that message with `2>/dev/null` and fell back to `launchctl load -w`, a legacy subcommand; the non-deprecated pair is `launchctl enable system/com.openssh.sshd` then `launchctl bootstrap system /System/Library/LaunchDaemons/ssh.plist`, which Homebrew itself migrated to ([homebrew-services #112](https://github.com/Homebrew/homebrew-services/pull/112)). The launchd route needs no FDA because Apple's status helper simply reads `SMJobIsEnabled(kSMDomainSystemLaunchd, CFSTR("com.openssh.sshd"))` and prints `Remote Login: on/off` ([apple-oss-distributions remote-login-status.c](https://github.com/apple-oss-distributions/OpenSSH/blob/main/remote-login-status.c)); the plist is socket-activated with `Disabled = true` and `SHAuthorizationRight = system.preferences`, so `sudo` is still required ([com.openssh.sshd.plist](https://github.com/apple-oss-distributions/OpenSSH/blob/main/com.openssh.sshd.plist)). The GUI path has an (i) button with an "Allow access for" pop-up (All users / Only these users) and, behind it, "Allow full disk access for remote users", which grants FDA to `/usr/libexec/sshd-keygen-wrapper` ([Apple mchlp1066, macOS 26 edition](https://support.apple.com/en-bn/guide/mac-help/allow-a-remote-computer-to-access-your-mac-mchlp1066/26/mac/26), snippet; [rtrouton/profiles](https://github.com/rtrouton/profiles/tree/main/EnableFullDiskAccessforSSH)). On Tahoe 26.1–26.2 that grant could not be seen in the Settings list even when it worked; Apple DTS confirmed a UI bug, fixed in 26.3 beta 1 ([Apple Developer Forums 806187](https://developer.apple.com/forums/thread/806187)).

The `--harden` drop-in is correct as written. Apple's build script inserts `Include /etc/ssh/sshd_config.d/*` near the top of the shipped `sshd_config` with the note that "Options that appear multiple times keep the first value set", and ships `100-macos.conf` (`UsePAM yes`, `AcceptEnv LANG LC_*`, `Include /etc/ssh/crypto.conf`), so the kit's `50-trimurti.conf` sorts first and wins ([xcscripts/make-config.zsh](https://github.com/apple-oss-distributions/OpenSSH/blob/main/xcscripts/make-config.zsh); [conf/100-macos.conf](https://github.com/apple-oss-distributions/OpenSSH/blob/main/conf/100-macos.conf)). `sshd -t` is the standard test flag ([sshd.8](https://github.com/apple-oss-distributions/OpenSSH/blob/main/openssh/sshd.8)), `launchctl kickstart -k system/com.openssh.sshd` is valid though unnecessary because launchd spawns sshd per connection, and Apple ships `sudo /usr/libexec/reset-ssh-configuration` to restore the default `/etc/ssh` while preserving host keys ([reset-ssh-configuration.zsh](https://github.com/apple-oss-distributions/OpenSSH/blob/main/reset-ssh-configuration.zsh)). Apple's `ssh-add` has `--apple-use-keychain` (the renamed `-K`) and `ssh_config` has the Apple-only `UseKeychain` (default `no`, incompatible with `PKCS11Provider`) ([ssh-add.1](https://github.com/apple-oss-distributions/OpenSSH/blob/main/openssh/ssh-add.1); [ssh_config.5](https://github.com/apple-oss-distributions/OpenSSH/blob/main/openssh/ssh_config.5)); GitHub's guide adds `IgnoreUnknown UseKeychain` for shared config files ([GitHub Docs](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/generating-a-new-ssh-key-and-adding-it-to-the-ssh-agent)). **Correction applied**: `enable-ssh-server.sh` now surfaces the FDA error, uses `enable` + `bootstrap` with `load -w` as last resort, README item 3 carries the (i)/"Allow access for"/FDA-checkbox text, `ssh-keys.sh` uses `--apple-use-keychain` on macOS and `ssh-config-gen.sh` emits `IgnoreUnknown UseKeychain` / `UseKeychain yes` / `AddKeysToAgent yes`. **Still open (optional)**: the `reset-ssh-configuration` note and the 26.1–26.2 UI-bug caveat.

## Tailscale and updates: a case-sensitive winget ID and a renamed cask

### Tailscale per OS, `--ssh` platform support, MagicDNS, key expiry (research question 6)

The Linux one-liner is the installer's own documented usage ([tailscale/tailscale scripts/installer.sh](https://github.com/tailscale/tailscale/blob/main/scripts/installer.sh)). On macOS the kit said `brew install --cask tailscale`; Homebrew's rename map now reads `"tailscale": "tailscale-app"` and the `tailscale-app` cask (1.102.4) installs `Tailscale-<ver>-macos.pkg`, the Standalone build Tailscale recommends, requiring `macos: :monterey` ([cask_renames.json](https://github.com/Homebrew/homebrew-cask/blob/master/cask_renames.json); [Casks/t/tailscale-app.rb](https://github.com/Homebrew/homebrew-cask/blob/master/Casks/t/tailscale-app.rb)). The `tailscale` formula is the CLI-only open-source `tailscaled` and conflicts with the cask ([Formula/t/tailscale.rb](https://github.com/Homebrew/homebrew-core/blob/main/Formula/t/tailscale.rb)). The GUI CLI lives at `/Applications/Tailscale.app/Contents/MacOS/Tailscale` and should be aliased, not symlinked, because a symlink "can cause the command to hang without any error" ([tailscale issue #3805](https://github.com/tailscale/tailscale/issues/3805)). On Windows the manifest is `PackageIdentifier: Tailscale.Tailscale`, a `burn` installer for `tailscale-setup-full-1.102.4.exe` ([winget-pkgs Tailscale/Tailscale](https://github.com/microsoft/winget-pkgs/tree/master/manifests/t/Tailscale/Tailscale)), and because `-e` "[u]ses the exact string in the query, including checking for case-sensitivity", the kit's lowercase `tailscale.tailscale -e` **matched nothing** ([winget install reference](https://github.com/microsoft/winget-cli/blob/master/doc/windows/package-manager/winget/install.md)).

The kit's "(Linux only)" comment on `--ssh` was wrong on both sides. ### PSWindowsUpdate over SSH and `winget upgrade --all` (research question 7)

This is the most serious finding in the kit. `update-all.ps1` ran `Get-WindowsUpdate -AcceptAll -Install -IgnoreReboot` inside a `try` and, on failure, printed a warning and continued to `REBOOT_REQUIRED=...` with exit 0. Every cmdlet exists and means what the kit assumed (`Install-WindowsUpdate` is literally "Equivalent Get-WindowsUpdate -Install"; `-IgnoreReboot` is "Do not ask for reboot if it needed, but do not reboot automaticaly"; `Get-WURebootStatus -Silent` "Return[s] true/false only") ([PSWindowsUpdate.xml help](https://github.com/mgajda83/PSWindowsUpdate/blob/main/PSWindowsUpdate/PSWindowsUpdate.xml)). But Microsoft documents `IUpdateSession::CreateUpdateInstaller` as returning "E_ACCESSDENIED — This method cannot be called from a remote computer" ([IUpdateSession::CreateUpdateInstaller](https://learn.microsoft.com/en-us/windows/win32/api/wuapi/nf-wuapi-iupdatesession-createupdateinstaller)), an SSH session is a network logon, and the module's own help says `Invoke-WUJob` exists precisely "because CreateUpdateDownloader() and CreateUpdateInstaller() methods can't be called from a remote computer - E_ACCESSDENIED" ([PSWindowsUpdate.xml help](https://github.com/mgajda83/PSWindowsUpdate/blob/main/PSWindowsUpdate/PSWindowsUpdate.xml)). Users report exactly this: `Install-WindowsUpdate` "despite running an elevated PowerShell shell with administrative privileges over SSH" fails with `0x80070005 (E_ACCESSDENIED)` ([PSWindowsUpdate #60](https://github.com/mgajda83/PSWindowsUpdate/issues/60); [Win32-OpenSSH #2083](https://github.com/PowerShell/Win32-OpenSSH/issues/2083)). Pushed through `run-remote.sh`, the kit's documented use, **the script never installed a Windows update and never said so loudly**. The fix is to run the install through `Invoke-WUJob -RunNow` (a local Task Scheduler job as SYSTEM) and poll its log, which `update-all.ps1` now does (lines 35–59), with `PendingFileRenameOperations` added to the reboot checks (line 77) while noting that anti-virus products use that key and cause false positives ([bcwilhite/PendingReboot](https://github.com/bcwilhite/PendingReboot)).

The winget flags the kit passes are all documented (`--all`, `--include-unknown`, `--silent`, `--accept-source-agreements`, `--accept-package-agreements`), and `--disable-interactivity` is the additional documented flag for non-interactive runs ([winget upgrade](https://learn.microsoft.com/en-us/windows/package-manager/winget/upgrade)). The exit-code comment was wrong: Microsoft's table maps `-1978335189` to `0x8A15002B APPINSTALLER_CLI_ERROR_UPDATE_NOT_APPLICABLE "No applicable update found"`, while the genuine already-installed codes are `0x8A150061` (`-1978335135`) and `0x8A15010D` (`-1978334963`), `0x8A15004F` is "not newer" and `0x8A15002C` (`-1978335188`) means `winget upgrade --all` "completed with failures" ([WinGet HRESULT codes](https://github.com/microsoft/winget-cli/blob/master/doc/windows/package-manager/winget/returnCodes.md)). Microsoft also documents that "WinGet will not be available until you have logged into Windows as a user for the first time", offering `Add-AppxPackage -RegisterByFamilyName -MainPackage Microsoft.DesktopAppInstaller_8wekyb3d8bbwe` and `Repair-WinGetPackageManager`, and that the CLI "is not supported in the system context" ([Use the WinGet tool](https://learn.microsoft.com/en-us/windows/package-manager/winget/); [WinGet troubleshooting](https://learn.microsoft.com/en-us/windows/package-manager/winget/troubleshooting)); SSH-session source failures are tracked in [winget-cli #5579](https://github.com/microsoft/winget-cli/issues/5579) and the still-open [#6334](https://github.com/microsoft/winget-cli/issues/6334). The other winget IDs check out: `OpenJS.NodeJS.LTS`, `Git.Git`, `Anthropic.ClaudeCode`, and the genuinely lowercase `smartmontools.smartmontools` ([winget-pkgs OpenJS/NodeJS/LTS](https://github.com/microsoft/winget-pkgs/tree/master/manifests/o/OpenJS/NodeJS/LTS); [Anthropic/ClaudeCode](https://github.com/microsoft/winget-pkgs/tree/master/manifests/a/Anthropic/ClaudeCode); [smartmontools](https://github.com/microsoft/winget-pkgs/tree/master/manifests/s/smartmontools/smartmontools)). On macOS, `update-all.sh` used `mas upgrade`; the mas README documents `update` (alias `upgrade`) and says it "require[s] root privileges" and prompts if sudo is not cached, and `softwareupdate` benefits from `--agree-to-license`; on Apple silicon OS updates need a volume-owner login (`--user`/`--stdinpass`), so unattended `-ia` may leave the OS update pending ([mas-cli README](https://github.com/mas-cli/mas/blob/main/README.md); [ss64 softwareupdate](https://ss64.com/mac/softwareupdate.html), snippet). **Correction applied**: `Invoke-WUJob`, `Find-Winget`, `--disable-interactivity`, the corrected exit-code comment, `$SUDO mas update`, `--agree-to-license`. **Still open**: tolerating `0x8A150061`/`0x8A15010D`/`0x8A15004F` in `Winget-Install` and warning on `-1978335188` after `upgrade --all`.

## Drive triage: a column-index bug graded failing drives too healthy (research question 10)

The kit's `-d auto` then `-d sat` fallback follows how smartctl works: `auto` guesses "from a matching USB ID entry in the drive database", `sat` is SCSI-to-ATA translation with 16-byte pass-through by default and `sat,12` the 12-byte variant, and `usbjmicron`, `usbsunplus`, `usbcypress` and `usbprolific` are the named bridge types ([smartctl(8)](https://raw.githubusercontent.com/smartmontools/smartmontools/master/smartmontools/smartctl.8.in)). Tracker tickets show that "Many unknown USB bridges only work with the '-d sat' option", a Seagate GoFlex needed `sat,12`, and an Iomega enclosure needed `usbjmicron` ([smartmontools ticket #332](https://www.smartmontools.org/ticket/332); [#720](https://www.smartmontools.org/ticket/720); [#1003](https://www.smartmontools.org/ticket/1003), snippets). Two script problems: the "did it work" test `grep -q 'SMART'` matched "SMART support is: Unavailable" and skipped the retry, while the real failure text ("Unknown USB bridge ... Please specify device type with the -d option") contains no such word; and `disk-triage.ps1` had no fallback at all. Both now use a five-step ladder (`auto`, `sat`, `sat,12`, `usbjmicron`, `usbsunplus`) with a health-line success test. On macOS the man page's Darwin note is "Use the OS X SAT SMART Driver to access SMART data on SAT capable USB and Firewire devices" and the vendor of the maintained fork states the external driver is not compatible on M-series Macs, so `SMART Status: Not Supported` there means unknown, not bad ([smartctl(8)](https://raw.githubusercontent.com/smartmontools/smartmontools/master/smartmontools/smartctl.8.in); [Volitans SMART Utility FAQ](https://www.volitans-software.com/support/smart-utility-faq/), snippet).

The parse bug is the data-loss item. smartctl's `-A` table has ten columns with RAW_VALUE in `$10`, and for formats such as `raw16(raw16)` (attribute 5) and `tempminmax` (194) it appends tokens like `(0 1)`, so `$NF` could return `1)`, the numeric test failed under `2>/dev/null`, and **the drive was reported one grade too healthy** ([drivedb.h](https://raw.githubusercontent.com/smartmontools/smartmontools/master/smartmontools/drivedb.h)). The verdict rule was consistent but incomplete: a pending sector is one the drive "would like to mark as 'bad' and reallocate" and an offline-uncorrectable sector "was not readable during an off-line scan or a self-test" ([smartd.conf(5)](https://raw.githubusercontent.com/smartmontools/smartmontools/master/smartmontools/smartd.conf.5.in)), which supports FAILING on 197/198, but Backblaze uses 5, 187, 188, 197 and 198 and "once SMART 187 goes above zero, drives are scheduled for replacement" ([Backblaze SMART stats](https://www.backblaze.com/docs/cloud-storage-hard-drive-smart-stats-and-failure-rates), snippet), and NVMe drives expose Media and Data Integrity Errors, Available Spare and Percentage Used beyond the Critical Warning byte ([nvmeprint.cpp](https://raw.githubusercontent.com/smartmontools/smartmontools/master/smartmontools/nvmeprint.cpp)). Because 198 only increments when something scans the surface, an untested drive's clean attributes prove less than they appear; the short test runs "usually under ten minutes", the extended "tens of minutes to several hours", both during normal operation, and `-l selftest` shows the last 21 results ([smartctl(8)](https://raw.githubusercontent.com/smartmontools/smartmontools/master/smartmontools/smartctl.8.in)). All of this is now in `disk-triage.sh` (`attr()` reads `$10`, 187/188/NVMe branches, `-l selftest`) and `hulk-drives.md` §4 gates repurposing on a long self-test.

Read-only inspection was not read-only. The kernel's ext4 guide states "ext4 will replay the journal (and thus write to the partition) even when mounted 'read only'. The mount options 'ro,noload' can be used to prevent writes" ([ext4 admin guide](https://raw.githubusercontent.com/torvalds/linux/master/Documentation/admin-guide/ext4.rst)); ntfs-3g's default `recover` option means "The Windows logfile is cleared" unless `ro` is given ([ntfs-3g(8)](https://raw.githubusercontent.com/tuxera/ntfs-3g/edge/src/ntfs-3g.8.in)); the ntfs3 driver's `force` is "Not recommended for use" ([ntfs3.rst](https://raw.githubusercontent.com/torvalds/linux/master/Documentation/filesystems/ntfs3.rst)); `blockdev --setro` is the belt-and-braces device-level block ([blockdev(8)](https://raw.githubusercontent.com/util-linux/util-linux/master/disk-utils/blockdev.8.adoc)); and Microsoft documents diskpart's `readonly` only as "specifies that the disk is read-only" with no statement of what it blocks ([attributes-disk.md](https://raw.githubusercontent.com/MicrosoftDocs/windowsserverdocs/main/WindowsServerDocs/administration/windows-commands/attributes-disk.md)). The kit named ddrescue but gave no commands; the standard sequence is `ddrescue -d -n SRC IMG MAP` then `ddrescue -d -r3 SRC IMG MAP` with the same mapfile, `-f` only for a device target, then `losetup -fP --show IMG` and `mount -o ro,noload` ([losetup(8)](https://raw.githubusercontent.com/util-linux/util-linux/master/sys-utils/losetup.8.adoc); [GNU ddrescue manual](https://www.gnu.org/software/ddrescue/manual/ddrescue_manual.html), snippet), with `ddrescue` 1.30 in Homebrew ([Formula/d/ddrescue.rb](https://raw.githubusercontent.com/Homebrew/homebrew-core/master/Formula/d/ddrescue.rb)). Copy verification was sound: rsync "normally verifies that each transferred file was correctly reconstructed ... by checking a whole-file checksum" and `--checksum` makes the dry run a genuine content comparison at the cost of reading everything on both sides ([rsync(1)](https://raw.githubusercontent.com/RsyncProject/rsync/master/rsync.1.md)); robocopy's `/COPY:DAT` is the default and `/R:2 /W:5` sensibly replace the defaults of 1,000,000 retries and 30 s, with `/L` as the list-only recheck ([robocopy.md](https://raw.githubusercontent.com/MicrosoftDocs/windowsserverdocs/main/WindowsServerDocs/administration/windows-commands/robocopy.md)); hashdeep's `-a -k` audit "is said to pass if each input file is matched against exactly one file in set of knowns" ([hashdeep(1)](https://raw.githubusercontent.com/jessek/hashdeep/master/man/hashdeep.1)).

Secure erase had a hard bug: hdparm's `--security-erase PWD` erases a "(locked) drive, using password PWD", and the required first step is `--security-set-pass NULL`, "a step omitted from almost all other sources"; the frozen state is lifted by S3 suspend for "a couple of minutes" ([hdparm(8)](https://raw.githubusercontent.com/Distrotech/hdparm/master/hdparm.8); [ATA wiki: Secure Erase](https://ata.wiki.kernel.org/index.php/ATA_Secure_Erase); [ArchWiki memory cell clearing](https://wiki.archlinux.org/title/Solid_state_drive/Memory_cell_clearing), snippets). `nvme format --ses=1` is correctly "User Data Erase", `--ses=2` is cryptographic erase, and `nvme sanitize` is the alternative ([nvme-format(1)](https://raw.githubusercontent.com/linux-nvme/nvme-cli/master/Documentation/nvme-format.txt); [nvme-sanitize(1)](https://raw.githubusercontent.com/linux-nvme/nvme-cli/master/Documentation/nvme-sanitize.txt)); coreutils warns that shred "assumes the file system and hardware overwrite data in place" ([shred.c](https://raw.githubusercontent.com/coreutils/coreutils/master/src/shred.c)); diskpart `clean all` "specifies that each and every sector on the disk is set to zero" ([clean.md](https://raw.githubusercontent.com/MicrosoftDocs/windowsserverdocs/main/WindowsServerDocs/administration/windows-commands/clean.md)). NIST SP 800-88 Rev. 1 is headed "Withdrawn" as of September 26, 2025, superseded by Rev. 2, which points to IEEE 2883-2022 ([NIST SP 800-88r1 PDF](https://nvlpubs.nist.gov/nistpubs/specialpublications/nist.sp.800-88r1.pdf), title only; [BitRaser summary](https://www.bitraser.com/article/nist-purge-standard.php), snippet). **Correction applied**: `$10` parsing, bridge ladder, self-test gate, `ro,noload` and `blockdev --setro`, ddrescue block, `--security-set-pass NULL`, robocopy `/L` recheck, hashdeep audit, NIST Rev. 2 label. **Still open (optional)**: an `hdparm -I` pre-check for "not frozen"/"enhanced erase", `--security-erase-enhanced` where supported, `nvme sanitize` as the alternative, and a note that the Rev. 2 detail rests on a vendor summary.

## Conclusion

The verification changes how much trust the kit deserves in each layer. The command layer, the parts copied from vendor quick-starts, was almost entirely right, and where it was wrong the error was a moved menu or a renamed cask. The failures clustered in the seams the vendors do not document as a unit: what a Windows network logon can and cannot do, what "read-only" means to a journaling filesystem, what a USB bridge hides from smartctl, and what an ATA drive requires before it will erase itself. Every tier-1 item shares the same shape: a command that looks like it ran, in a script that exits 0, so the operator would only learn of the gap when a machine missed a patch cycle or a reused drive failed. That argues for the kit's own verification step (`verify.sh`) growing an assertion per silent-failure path, such as checking `Get-WUHistory` for a recent install rather than trusting `REBOOT_REQUIRED=no`, and for `disk-triage` printing the raw column it parsed so a `1)` would be visible.

The second implication is about sourcing. Half of the primary hosts were unreachable, and the researchers' workaround, reading Microsoft, TrueNAS, Apple and Tailscale documentation from their public source repositories, produced verbatim quotes with dated `ms.date` stamps that are arguably more auditable than a rendered page. The router and Synology/QNAP sections could not be rescued that way, and their corrections, though consistent across multiple snippets, should be spot-checked on a real router admin page and a real DSM/QTS install before the checklists are treated as authoritative. With commit `cccdb95` in place the kit is safe to run; the open items in the table are wording, and none of them changes what a script does.
