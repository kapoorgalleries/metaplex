## Key question 1: Official install commands and which is recommended (npm, brew, npx, MacPorts, Windows)

### Takeaway
The kit's `npm install -g @google/gemini-cli@latest` on every platform is exactly the official "standard" method; Homebrew and MacPorts are official alternatives on macOS/Linux, `npx` is listed only as an "advanced" way to run without installing, and there is no Windows-specific installer (npm on Node 20+ under PowerShell is the documented Windows route). No correction needed; two optional additions.

## Key question 3: How to update and how to print the version

### Takeaway
The official update command for an npm install is the same `npm install -g @google/gemini-cli@latest` the kit already runs; Homebrew installs are updated with `brew upgrade gemini-cli`; the CLI also auto-updates itself on launch for npm-global installs (setting `general.enableAutoUpdate`, default `true`). The cheatsheet lists a `gemini update` command, but the published 0.60.0 bundle registers no such top-level command and the feature request for it was closed "not planned", so the kit should not adopt it. `gemini --version` (alias `-v`) is the official version print.

### Cited Findings
- Stable channel: "The stable release uses the `latest` tag. Omitting the tag also installs the latest stable release by default. `npm install -g @google/gemini-cli` / `npm install -g @google/gemini-cli@latest` — Both commands install the latest stable release." Preview: `npm install -g @google/gemini-cli@preview`; Nightly: `npm install -g @google/gemini-cli@nightly` — [docs/get-started/installation.mdx](https://github.com/google-gemini/gemini-cli/blob/main/docs/get-started/installation.mdx)
- Release cadence: "New stable releases will be published each week at UTC 20:00 on Tuesdays ... Use `latest` tag"; "New preview releases will be published each week at UTC 23:59 on Tuesdays"; nightly "each day at UTC 00:00" — [README.md](https://github.com/google-gemini/gemini-cli/blob/main/README.md)
- `--version` / `-v`: "Show CLI version number and exit" — [docs/cli/cli-reference.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/cli/cli-reference.md); also "`--version`: Displays the version of the CLI." — [docs/reference/configuration.md](https://github.com/google-gemini/gemini-cli/blob/main/docs/reference/configuration.md)

## Key question 4: Every auth route with exact commands/env vars, and the settings.json auth key

### Takeaway
Three official routes: (1) "Sign in with Google" OAuth (menu label is "Sign in with Google", not "Login with Google"; Workspace/company/school accounts and Code Assist licence holders must also set `GOOGLE_CLOUD_PROJECT`), (2) Gemini API key from AI Studio via `GEMINI_API_KEY`, (3) Vertex AI via ADC / service-account JSON / `GOOGLE_API_KEY`, all with `GOOGLE_CLOUD_PROJECT` + `GOOGLE_CLOUD_LOCATION` (or `GOOGLE_API_KEY` for express mode). The persisted choice lives in `~/.gemini/settings.json` under `security.auth.selectedType` with values `oauth-personal` | `gemini-api-key` | `vertex-ai` (plus `cloud-shell`, `compute-default-credentials`, `gateway` in the enum); the old top-level `selectedAuthType` was migrated in 2025. The kit's wording "Login with Google" should become "Sign in with Google", and the Workspace `GOOGLE_CLOUD_PROJECT` requirement should be added.

## Key question 5: Headless / no-browser flow (`NO_BROWSER=true`), alternatives, and where OAuth credentials are cached

### Takeaway
`NO_BROWSER=true gemini` does exactly what the kit says: the CLI prints "Please visit the following URL to authorize the application:" followed by a URL, then prompts "Enter the authorization code: " (5-minute timeout, two attempts). This is implemented in source and referenced by the CLI's own error text, but it is not described on the documentation pages; over SSH the browser is suppressed automatically anyway (`SSH_CONNECTION` set, or Linux without `DISPLAY`/`WAYLAND_DISPLAY`), and the flow needs an interactive TTY. There is no `--auth` flag. OAuth tokens are kept in the OS keychain (service `gemini-cli-oauth`) with a legacy/fallback file `~/.gemini/oauth_creds.json` that is migrated on first load; the docs' recommended headless route is an API key or Vertex.

### Cited Findings

- Automatic suppression heuristics ("adaptation of the logic from the Google Cloud SDK"): returns false when `BROWSER=www-browser`, when `CI` is set or `DEBIAN_FRONTEND=noninteractive`, on Linux when none of `DISPLAY`, `WAYLAND_DISPLAY`, `MIR_SOCKET` is set, and on non-Linux when `SSH_CONNECTION` is set ("If in an SSH session on a non-Linux OS (e.g., macOS), don't launch browser.") — [packages/core/src/utils/browser.ts](https://github.com/google-gemini/gemini-cli/blob/main/packages/core/src/utils/browser.ts)

### Inferences
- Because the kit's `run-remote.sh` pushes scripts over SSH, any attempt to log Gemini in from a non-TTY remote command will hit the "non-interactive" fatal error; the login must be done in an interactive `ssh -t` session or locally, or the machine should be provisioned with `GEMINI_API_KEY` in `~/.gemini/.env` instead.
- On Linux desktops reached over SSH with X forwarding (`DISPLAY` set) the CLI will try to open a browser on the remote box; `NO_BROWSER=true` is what prevents that, so the kit's explicit variable is the right advice even though it is often redundant.
- Headless credential storage on a server without a keychain daemon falls back to the file store, so `~/.gemini/oauth_creds.json` is the path to back up or wipe on Linux boxes; the exact fallback condition is in `HybridTokenStorage`, which I did not read.

### Gaps
- `NO_BROWSER` is undocumented on the docs pages fetched; only the source and the CLI's runtime messages reference it. I could not view the rendered site to confirm whether any page (e.g. an FAQ) mentions it.
- The name of the env var that forces encrypted-file credential storage (`FORCE_ENCRYPTED_FILE_ENV_VAR`) was not resolved from the fetched files.
- Windows OpenSSH sessions: the heuristic suppresses the browser whenever `SSH_CONNECTION` is set on non-Linux; I did not verify that Windows OpenSSH server sets that variable for PowerShell sessions, so keep the kit's explicit `$env:NO_BROWSER = 'true'`.
