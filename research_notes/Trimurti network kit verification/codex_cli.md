## Key Question 1: Official install methods per OS and which one OpenAI recommends

### Takeaway

## Key Question 2: Windows support — native vs. WSL2, and caveats

### Takeaway
Native Windows is now a first-class, officially documented target (PowerShell installer, npm win32 packages, and a native Windows sandbox with `[windows] sandbox = "elevated" | "unelevated"` in `config.toml`), and the official Windows page tells users to "Use the native Windows sandbox by default" and pick WSL only for Linux-native tooling; the repo's `docs/install.md` still says "Windows 11 via WSL2" (stale), and OpenAI's own November 2025 announcement called the native sandbox "highly experimental" with no later official "stable" statement found.

### Cited Findings

What the kit says:
- `bootstrap-ai-clis.ps1` header (lines 2-5): "Install Claude Code, OpenAI Codex CLI and Gemini CLI on this Windows machine, plus Node.js LTS (Codex and Gemini are npm packages and need Node 20+) and, with -WithGit, Git for Windows so Claude Code gets a Bash tool." The script installs Codex natively on Windows via npm and says nothing about WSL or sandboxing — [kit file](/home/user/metaplex/ops/network/scripts/bootstrap-ai-clis.ps1)

What the official sources say:
- README gives a first-class Windows install command: `powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"` — [openai/codex README](https://github.com/openai/codex/blob/main/README.md)
- npm publishes `@openai/codex-win32-x64` and `@openai/codex-win32-arm64` platform packages at 0.155.1, and `bin/codex.js` maps `win32` to `x86_64-pc-windows-msvc` / `aarch64-pc-windows-msvc` — [npm registry](https://registry.npmjs.org/@openai/codex/latest)
- The repo's `docs/install.md` "System requirements" table still reads: "Operating systems | macOS 12+, Ubuntu 20.04+/Debian 10+, or Windows 11 **via WSL2**"; "Git (optional, recommended) | 2.23+ for built-in PR helpers"; "RAM | 4-GB minimum (8-GB recommended)". - OpenAI staff (@ae-openai) opened discussion "Help test experimental Windows sandbox" on November 1, 2025: "If you use the CLI on native windows, you can enable a highly experimental filesystem and network sandbox", initially enabled with `--enable enable_experimental_windows_sandbox --sandbox workspace-write --ask-for-approval on-request`; a February 12, 2026 comment shows the config form `approval_policy = "on-request"`, `sandbox_mode = "workspace-write"`, `[features] elevated_windows_sandbox = true`; caveat quoted: it "does not prevent file writes, deletions, or creations in any directory where the Everyone SID already has write permissions"; the thread contains "no official statement indicating the sandbox became default or stable" through June 2026 — [openai/codex discussion #6065](https://github.com/openai/codex/discussions/6065)
- (snippet) developers.openai.com/codex/windows: "Native Windows sandbox support includes two modes that you can configure in config.toml: `[windows] sandbox = "elevated" # or "unelevated"` ... elevated is the preferred native Windows sandbox. It uses dedicated lower-privilege sandbox users, filesystem permission boundaries, firewall rules, and local policy changes"; "Unelevated ... runs commands with a restricted Windows token derived from your current user, applies ACL-based filesystem boundaries"; "Use the native Windows sandbox by default. Choose WSL when you need Linux-native tooling, your workflow already lives in WSL2, or neither native Windows sandbox mode meets your needs."; "By default, both sandbox modes also use a private desktop for stronger UI isolation. - (snippet) developers.openai.com/codex/app/windows: "The ChatGPT desktop app on Windows supports a native Windows sandbox when the agent runs in PowerShell, and uses Linux sandboxing when you run the agent in Windows Subsystem for Linux 2 (WSL2)"; for Node on Windows it suggests `winget install --id OpenJS.NodeJS.LTS` — [developers.openai.com/codex/app/windows](https://developers.openai.com/codex/app/windows) (blocked; snippet)

- Node/npm on native Windows: no official caveat found about npm-installed Codex on Windows beyond the PowerShell selection fix above.

## Key Question 3: Node.js version requirement for the npm package

### Takeaway
The only authoritative Node requirement is the package's own `"engines":{"node":">=16"}`; OpenAI publishes no separate Node minimum for the CLI (the "Node 18+" seen on the docs site is for the separate `@openai/codex-sdk`), and since `bin/codex.js` just spawns a native binary, the kit's "Codex ... need 20+" is a Gemini requirement mis-attributed to Codex, harmless but inaccurate.

### Cited Findings

What the kit says:
- `bootstrap-ai-clis.sh` line 41: `log "installing Node.js 22 (Codex and Gemini need 20+)"`; line 37: `node_ok() { have node && [ "$(node -p 'process.versions.node.split(".")[0]')" -ge 20 ]; }` — [kit file](/home/user/metaplex/ops/network/scripts/bootstrap-ai-clis.sh)
- `bootstrap-ai-clis.ps1` line 37: `Log 'installing Node.js LTS (Codex and Gemini need 20+)'; Winget-Install 'OpenJS.NodeJS.LTS'` — [kit file](/home/user/metaplex/ops/network/scripts/bootstrap-ai-clis.ps1)

What the official sources say:
- npm registry metadata for `@openai/codex@0.155.1`: `"engines":{"node":">=16"}` — [npm registry](https://registry.npmjs.org/@openai/codex/latest)
- `bin/codex.js` is an ES module (`#!/usr/bin/env node`, `import { spawn } from "node:child_process"`, `import.meta.url`, `createRequire`) whose only job is to pick the platform package and spawn the native `codex` binary (observed in the locally installed package) — [npm registry](https://registry.npmjs.org/@openai/codex/latest)
- README, docs/install.md and the CLI help mention no Node version at all; docs/install.md says "Codex is written in Rust, so it honors the `RUST_LOG` environment variable" — [docs/install.md](https://github.com/openai/codex/blob/main/docs/install.md)
- (snippet) developers.openai.com/codex/sdk: "The library requires Node.js 18 or later for server-side usage" — this is the `@openai/codex-sdk` package, not the CLI — [developers.openai.com/codex/sdk](https://developers.openai.com/codex/sdk) (blocked; snippet)

### Inferences
- `engines >=16` is authoritative for what npm will refuse to install; nothing official raises it. The kit's Node 20+ floor is driven by Gemini CLI, which is fine, but the log lines should not claim Codex needs it.
- Exact corrected text, `bootstrap-ai-clis.sh` line 41: `log "installing Node.js 22 (Gemini CLI needs 20+; Codex's npm package only needs 16+)"`; `bootstrap-ai-clis.ps1` line 37: `Log 'installing Node.js LTS (Gemini CLI needs 20+; Codex npm package needs 16+)'`. If Codex moves to the official installer, drop Codex from these lines entirely.

### Gaps
- No official statement of a Node minimum for the CLI on developers.openai.com could be quoted (domain blocked); absence in README/docs is confirmed, absence on the docs site is inferred from snippets.

## Key Question 4: All login routes, which ChatGPT plans include Codex, and whether an API key is "additional setup"

### Takeaway

## Key Question 7: Is the npm route on all three OSes still the best choice for this kit?

### Takeaway
npm is still officially supported everywhere and is the least-change option because the kit already installs Node for Gemini, but OpenAI's headline route in 2026 is the standalone installer (`install.sh` / `install.ps1`), which removes the Node coupling, verifies SHA-256 digests, manages PATH itself, and is what `codex update` uses for self-service updates; either is defensible, and I would recommend moving Codex to the official installers on all three OSes (or at minimum on Windows) while keeping npm as a documented fallback.

### Cited Findings
- README ordering: standalone installers first ("Run the following on Mac or Linux to install Codex CLI"), then "Codex CLI can also be installed via the following package managers" (npm, Homebrew cask), then GitHub binaries — [openai/codex README](https://github.com/openai/codex/blob/main/README.md)
- The npm package is only a launcher for the same native binaries the installer downloads (`bin/codex.js` spawns `@openai/codex-<platform>`; `engines.node >=16`) — [npm registry](https://registry.npmjs.org/@openai/codex/latest)
- Installer defaults: Unix `~/.local/bin/codex` with profile PATH management and `CODEX_NON_INTERACTIVE=1`; Windows `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin` with PATH management, `CODEX_INSTALL_DIR` override, digest verification (`Test-ArchiveDigest`, `Get-FileHash ... SHA256`) — [scripts/install/install.sh](https://github.com/openai/codex/blob/main/scripts/install/install.sh); [scripts/install/install.ps1](https://github.com/openai/codex/blob/main/scripts/install/install.ps1)
- `codex update` covers npm, bun, pnpm, vp, brew and both standalone installers, so update handling is uniform whichever route is chosen — [codex-rs/tui/src/update_action.rs](https://github.com/openai/codex/blob/main/codex-rs/tui/src/update_action.rs)
- Homebrew is macOS-and-Linux capable for Codex (cask carries `arm64_linux`/`x86_64_linux` builds) but the formula-to-cask switch in October 2025 caused stuck-version confusion ("formula overrides cask") — [homebrew-cask Casks/c/codex.rb](https://github.com/Homebrew/homebrew-cask/blob/master/Casks/c/codex.rb); [openai/codex issue #5317](https://github.com/openai/codex/issues/5317); [buildwithmatija.com (community)](https://www.buildwithmatija.com/commands/brew-fix-codex-formula-vs-cask-conflict)
- Gemini CLI remains an npm package in the kit (`@google/gemini-cli@latest`), so Node 20+ is installed regardless of the Codex choice — [kit file](/home/user/metaplex/ops/network/scripts/bootstrap-ai-clis.sh)
- The kit already adds `~/.local/bin` to PATH for Claude Code (`bootstrap-ai-clis.sh` line 79: `ensure_path "$HOME/.local/bin"`; `update-all.sh` line 17 exports it), which is exactly the Codex installer's default `BIN_DIR` — [kit file](/home/user/metaplex/ops/network/scripts/bootstrap-ai-clis.sh)

### Inferences
- Reasons to keep npm: one mechanism for two CLIs; Node is already present for Gemini; `npm install -g ...@latest` is idempotent and exactly what `codex update` runs for npm installs; officially listed on the README; works natively on Windows (win32 packages exist).
- Reasons to prefer the official installer: it is OpenAI's first-listed route; no dependency on npm's global prefix/permissions (`setup_npm_prefix` workaround becomes unnecessary for Codex); the installer verifies digests and can pin `--release VERSION`; installs land in `~/.local/bin` (already on the kit's PATH) and `%LOCALAPPDATA%\Programs\OpenAI\Codex\bin`; `codex update` then self-updates via the installer with `CODEX_NON_INTERACTIVE=1`; on Windows it avoids the npm `Refresh-Path`/"node not on PATH" failure mode the ps1 already has to guard against (line 38). Drawback: this sandbox could not reach chatgpt.com, so the kit's `run-remote.sh` targets must be able to reach `chatgpt.com` and `releases.openai.com` (fallback `github.com`); npm needs only `registry.npmjs.org`.
- Reasons not to make Homebrew the primary macOS route: it is fine (`brew install --cask codex`, `brew upgrade --cask codex`) but adds nothing over the installer and has the formula/cask history; use it only where a Mac is already brew-managed.
- Recommended kit text if switching (all three OSes): `.sh`: `install_codex() { log "installing/updating Codex CLI (official installer)"; curl -fsSL https://chatgpt.com/codex/install.sh | CODEX_NON_INTERACTIVE=1 sh; ensure_path "$HOME/.local/bin"; }` and remove Codex from the Node gate (`if [ "$SKIP_GEMINI" = 1 ]; then SKIP_NODE=1; fi`); `.ps1`: `if (-not $SkipCodex) { Log 'installing/updating Codex CLI (official installer)'; $env:CODEX_NON_INTERACTIVE = '1'; Invoke-Expression (Invoke-RestMethod -Uri 'https://chatgpt.com/codex/install.ps1'); Refresh-Path }`; `update-all.*`: replace the `@openai/codex` npm loop entry with `codex update`. If not switching, the only required kit edits are the comment/log-line attributions in Q3 and the sign-in additions in Q4/Q5.

### Gaps
- No official OpenAI statement ranks npm vs installer explicitly ("recommended" wording could not be quoted from the blocked docs site); the recommendation above rests on README ordering, installer features read from source, and the kit's own constraints.
- Installer behaviour on a machine where `~/.local/bin` is not yet on PATH in a non-login SSH shell (the kit's `run-remote.sh` case) was not tested; `install.sh`'s `add_to_path` writes to a profile file, and the kit's `ensure_path` would cover the current session.
