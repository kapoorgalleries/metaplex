## Q2. Firewall rule `OpenSSH-Server-In-TCP` and whether `Add-WindowsCapability` already creates it

### Takeaway
The kit's `New-NetFirewallRule -Name 'OpenSSH-Server-In-TCP' -DisplayName 'OpenSSH Server (sshd)' -Enabled True -Direction Inbound -Protocol TCP -Action Allow -LocalPort 22` guarded by a `Get-NetFirewallRule` check is character-for-character Microsoft's documented command; Microsoft states installing the server "creates and enables" the rule and asks you to verify and create it only if missing.

### Cited Findings

- Microsoft: "Installing OpenSSH Server creates and enables a firewall rule named `OpenSSH-Server-In-TCP`. This rule allows inbound SSH traffic on port 22. - Microsoft: "`# Confirm the Firewall rule is configured. It should be created automatically by setup. ### Inferences
- No correction needed. Because neither Microsoft's nor the kit's command passes `-Profile`, the rule the kit creates is assigned to `Any` profile, i.e. it admits SSH on Public networks too (this matters for Q5).

### Gaps

## Q3. Key-based auth for administrators: `administrators_authorized_keys`, ignored per-user file, `Match Group administrators`, the exact `icacls` command, and Microsoft's copy-key one-liner

### Takeaway
Microsoft confirms that for members of the administrators group sshd uses `%programdata%\ssh\administrators_authorized_keys` instead of `.ssh/authorized_keys`, that the file must carry ACEs only for `NT Authority\SYSTEM` and `BUILTIN\Administrators`, and its documented command is `icacls.exe "C:\ProgramData\ssh\administrators_authorized_keys" /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"` — the kit uses that exact ACL in both `enable-ssh-server.ps1` and `ssh-keys.sh`. The per-user file is ignored for admins only because of the `Match Group administrators` block that ships at the end of the default `sshd_config`.

### Cited Findings
- Kit (server script): `$adminKeys = 'C:\ProgramData\ssh\administrators_authorized_keys'` ... `if (-not (Select-String -Path $adminKeys -SimpleMatch -Pattern $PublicKey -Quiet)) { Add-Content -Path $adminKeys -Value $PublicKey }` / `& icacls.exe $adminKeys /inheritance:r /grant 'Administrators:F' /grant 'SYSTEM:F' | Out-Null` — [enable-ssh-server.ps1 lines 48–56](/home/user/metaplex/ops/network/scripts/enable-ssh-server.ps1)
- Kit (push from admin machine): `cat <<EOF | ssh -o ConnectTimeout=8 -o StrictHostKeyChecking=accept-new -p "$3" "$1@$2" "powershell -NoProfile -ExecutionPolicy Bypass -Command -"` ... `\$isAdmin = ([Security.Principal.WindowsPrincipal][Security.Principal.WindowsIdentity]::GetCurrent()).IsInRole([Security.Principal.WindowsBuiltInRole]::Administrator)` / `if (\$isAdmin) { \$f = 'C:\ProgramData\ssh\administrators_authorized_keys' } else { \$f = Join-Path \$env:USERPROFILE '.ssh\authorized_keys' }` ... `if (\$isAdmin) { icacls.exe \$f /inheritance:r /grant 'Administrators:F' /grant 'SYSTEM:F' | Out-Null }` — [ssh-keys.sh lines 44–55 (`push_windows`)](/home/user/metaplex/ops/network/scripts/ssh-keys.sh)
- Kit header comment: "for any user in the Administrators group, sshd ignores %USERPROFILE%\.ssh\authorized_keys and reads C:\ProgramData\ssh\administrators_authorized_keys instead, and that file must be ACL'd to Administrators + SYSTEM only or sshd refuses it." — [enable-ssh-server.ps1 lines 7–10](/home/user/metaplex/ops/network/scripts/enable-ssh-server.ps1)
- Microsoft, `AuthorizedKeysFile`: "The default is `.ssh/authorized_keys`. If you don't specify an absolute path, OpenSSH looks for the file relative to your home directory, such as `C:\Users\username`. If the user belongs to the administrator group, `%programdata%/ssh/administrators_authorized_keys` is used instead." — [OpenSSH Server configuration for Windows Server and Windows, ms.date 08/05/2025](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-server-configuration) (source: `openssh-server-configuration.md`)
- Microsoft, same page (TIP): "The administrators_authorized_keys file must only have permission entries for the `NT Authority\SYSTEM` account and `BUILTIN\Administrators` security group. The NT Authority\SYSTEM account must be granted full control. The `BUILTIN\Administrators` security group is required to enable administrators to manage the authorized keys. You can choose the required access. To grant permissions, you can open an elevated PowerShell prompt and run the command `icacls.exe "C:\ProgramData\ssh\administrators_authorized_keys" /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"`." — [same](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-server-configuration)
- Microsoft, key management page, "Administrative user": "You need to place the contents of your public key (\.ssh\id_ecdsa.pub) on the server into a text file called `administrators_authorized_keys` in C:\ProgramData\ssh\. ... The ACL on this file needs to be configured to only allow access to administrators and the System user." and the NOTE: "This example shows the steps for creating the `administrators_authorized_keys` file. This file only applies to administrator accounts. You must use it instead of the user-specific file within the user's profile location." — [Key-based authentication in OpenSSH for Windows, ms.date 10/03/2025](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh_keymanagement)
- Microsoft's documented copy-key one-liner (administrative user), verbatim:

  $authorizedKey = Get-Content -Path $env:USERPROFILE\.ssh\id_ecdsa.pub

  # Generate the PowerShell command to run remotely that copies the public key file generated previously on your client to the authorized_keys file on your server.

  ```

- Win32-OpenSSH wiki ACL recipe: "This file should only be accessible by SYSTEM and Administrators group. - Microsoft, sshd_config location: "OpenSSH Server reads configuration data from `%programdata%\ssh\sshd_config` by default ... ### Inferences
- No functional correction needed: the kit's approach (Add-Content + `icacls /inheritance:r /grant Administrators:F /grant SYSTEM:F`) is Microsoft's, and feeding the script over stdin to `powershell -Command -` is a valid substitute for Microsoft's argument-string one-liner that also works whatever `DefaultShell` is set to.
- The statement "`%USERPROFILE%\.ssh\authorized_keys` is ignored for administrators unless the `Match Group administrators` lines are removed" is an inference from the default `sshd_config` (Microsoft only says the ProgramData file "is used instead"). Removing/commenting the two `Match Group administrators` lines at the end of `C:\ProgramData\ssh\sshd_config` and `Restart-Service sshd` makes admins fall back to the global `AuthorizedKeysFile .ssh/authorized_keys`. The kit does not need this; it could be added to README item 1 as an alternative.
- Optional robustness change (both files), using Microsoft's SID advice so the command survives non-English Windows: replace `/grant 'Administrators:F' /grant 'SYSTEM:F'` with `/grant '*S-1-5-32-544:F' /grant '*S-1-5-18:F'` (`S-1-5-18` is the well-known SID for `NT AUTHORITY\SYSTEM`; Microsoft's own example only converts the Administrators group and keeps `SYSTEM:F`).
- Because a key-authenticated SSH session carries no credentials, anything run through `run-remote.sh` on a Windows host that needs the user's identity on the network (mapped NAS shares, `net use`, DPAPI-protected secrets) will fail; that is by design and worth a README note.

### Gaps
- Microsoft's page does not say the *per-user* file is "ignored" in so many words; the closest is "is used instead". No Microsoft text was found endorsing removal of the `Match Group administrators` block (a third-party write-up on this, journal.jadaptive.com, is blocked by the proxy).

## Q4. `DefaultShell` registry value (and `DefaultShellCommandOption`)

### Takeaway
Microsoft documents exactly what the kit does: a `String` value `DefaultShell` under `HKLM:\SOFTWARE\OpenSSH` holding the full path to the shell, set with `New-ItemProperty ... -PropertyType String -Force`; `DefaultShellCommandOption` is an optional value documented on the project wiki with default `-c`, which `powershell.exe`/`pwsh.exe` accept, so no change is needed.

### Cited Findings
- Kit: `$shell = 'C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe'` / `if ($Pwsh7 -and (Test-Path 'C:\Program Files\PowerShell\7\pwsh.exe')) { $shell = 'C:\Program Files\PowerShell\7\pwsh.exe' }` / `if (-not (Test-Path 'HKLM:\SOFTWARE\OpenSSH')) { New-Item -Path 'HKLM:\SOFTWARE\OpenSSH' -Force | Out-Null }` / `New-ItemProperty -Path 'HKLM:\SOFTWARE\OpenSSH' -Name DefaultShell -Value $shell -PropertyType String -Force | Out-Null` — [enable-ssh-server.ps1 lines 43–46](/home/user/metaplex/ops/network/scripts/enable-ssh-server.ps1)
- Microsoft: "The initial default in Windows is the Windows command prompt (cmd.exe) ... You can configure the default ssh shell in the Windows registry by adding the full path to the shell executable to `HKEY_LOCAL_MACHINE\SOFTWARE\OpenSSH` in the string value `DefaultShell`. The following example elevated PowerShell command sets the default shell to be `powershell.exe` for OpenSSH Server. (Setting this path doesn't apply to OpenSSH Client.)
  ```powershell
  $NewItemPropertyParams = @{
      Path         = "HKLM:\SOFTWARE\OpenSSH"
      Name         = "DefaultShell"
      Value        = "C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe"
      PropertyType = "String"
      Force        = $true
  }

  ```" — [OpenSSH Server configuration, ms.date 08/05/2025](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-server-configuration)
- Microsoft prerequisite: "To set the default command shell, first confirm that the OpenSSH installation folder is on the system path. For Windows, the default installation folder is `%systemdrive%\Windows\System32\openssh`." — [same](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-server-configuration)
- Wiki: "`Computer\HKEY_LOCAL_MACHINE\SOFTWARE\OpenSSH\DefaultShell` - full path of the shell executable; `...\DefaultShellCommandOption` (optional) - switch that the configured default shell requires to execute a command, immediately exit and return to the calling process. By default this is `-c`. `...\DefaultShellEscapeArguments` (optional) - flag that allow you to skip escaping the arguments of default shell. By default this is `0`. ## Q6. Are SSH sessions for Administrators-group users elevated (full token) by default, so MSI installs and `Add-WindowsCapability` succeed over SSH?

### Takeaway
Primary-source evidence says yes: the Win32-OpenSSH maintainers closed issue #1652 "SSH login has full admin rights and there's no way to not grand them" as *Resolution - Answered*, the project wiki's whole rationale for locking `administrators_authorized_keys` to Administrators+SYSTEM is that a non-elevated admin process must not be able to add keys, and users report running elevated shells over SSH; however, the session is a *network* logon (type 3), which is why Windows Update's COM API still refuses it (Q7) and why key-based sessions have no outbound credentials (Q3).

### Cited Findings
- Kit claims: "Run elevated (an SSH session as an administrator already is)" — [update-all.ps1 line 4](/home/user/metaplex/ops/network/scripts/update-all.ps1); "Node's MSI needs elevation: run from an elevated PowerShell, or over SSH as a member of Administrators (those SSH sessions are already elevated)." — [bootstrap-ai-clis.ps1 lines 7–9](/home/user/metaplex/ops/network/scripts/bootstrap-ai-clis.ps1)
- Win32-OpenSSH issue #1652, opened August 17, 2020 by Nikos Chantziaras, title "SSH login has full admin rights and there's no way to not grand them"; body: SSH logins receive full administrator privileges with no option to disable it, and the suggested `DenyGroups Administrators` prevents login entirely rather than reducing privileges; status Closed, label "Resolution - Answered" — [PowerShell/Win32-OpenSSH#1652](https://github.com/PowerShell/Win32-OpenSSH/issues/1652) (GitHub issue; maintainer comments could not be retrieved through the proxy)
- Wiki rationale: "Its important to understand the distinction between 'AdministratorsGroup' and an admin user. A logged on admin user would typically run processes in non-elevated mode. Even though an admin user is part of AG, these non-elevated processes **do not have authority** to access resources that are locked only to AG." — [Win32-OpenSSH wiki: Security protection of various files](https://github.com/PowerShell/Win32-OpenSSH/wiki/Security-protection-of-various-files-in-Win32-OpenSSH)
- Microsoft: "PermitRootLogin: Not applicable in Windows. To prevent administrators from signing in, use Administrators with the `DenyGroups` directive." — [OpenSSH Server configuration](https://learn.microsoft.com/en-us/windows-server/administration/openssh/openssh-server-configuration)
- User report: PSWindowsUpdate issue #60 (opened September 12, 2025, open) says that "despite running an elevated PowerShell shell with administrative privileges over SSH", `Install-WindowsUpdate -MicrosoftUpdate` fails with `Access is denied (Exception from HRESULT: 0x80070005 (E_ACCESSDENIED))` — [mgajda83/PSWindowsUpdate#60](https://github.com/mgajda83/PSWindowsUpdate/issues/60) (GitHub issue)
- Logon type: with sshd running as LocalSystem, an SSH key logon yields "`NT AUTHORITY\NETWORK`, SID `S-1-5-2` → a Network logon (type 3) — no credential store, DPAPI locked" — [gist by YoraiLevi (non-Microsoft, last active July 4, 2026)](https://gist.github.com/YoraiLevi/49da57da5c7bb4724ba3f4e4c694d748)
- Source: Win32-OpenSSH creates the user token with `LsaLogonUser(... Network ...)` via S4U (`KERB_S4U_LOGON` / `MSV1_0_S4U_LOGON`) for key auth and `LogonUserExExW(..., LOGON32_LOGON_NETWORK_CLEARTEXT, ...)` for password auth; the file contains no `TokenLinkedToken`/`TokenElevation` handling — [PowerShell/openssh-portable contrib/win32/win32compat/win32_usertoken_utils.c (latestw_all)](https://github.com/PowerShell/openssh-portable/blob/latestw_all/contrib/win32/win32compat/win32_usertoken_utils.c)
- Design note: "End result of authentication in Windows is a Windows user token (if authentication succeeds). SSH sessions that need client user capabilities are hosted in processes running under the context of client user (launched using CreateProcess(user_token))." — [Win32-OpenSSH wiki: About Win32-OpenSSH and Design Details](https://github.com/PowerShell/Win32-OpenSSH/wiki/About-Win32-OpenSSH-and-Design-Details)
- winget's own docs on elevation: "When running WinGet in an Administrator Command Prompt, you will not see elevation prompts if the application requires it." — [Use the WinGet tool, ms.date 03/24/2026](https://learn.microsoft.com/en-us/windows/package-manager/winget/) (source: MicrosoftDocs/windows-dev-docs `hub/package-manager/winget/index.md`)

### Inferences
- Keep the kit's claim; it is consistent with every primary source found (and `enable-ssh-server.ps1`/`ssh-keys.sh` themselves depend on it: `IsInRole(Administrator)` inside the SSH session returns True only on an elevated token). MSI installs via winget and `Add-WindowsCapability` therefore do not hit UAC over SSH.
- Add one caveat sentence next to the "already elevated" comments: "It is a network-type logon: Windows Update's COM API, DPAPI and outbound credential use still refuse it (see update-all.ps1)."
- The elevation is a property of the token LSA returns for the sshd (SYSTEM)-initiated S4U/network logon, not of explicit code in Win32-OpenSSH; nothing in Microsoft's docs promises it, so treat it as observed behaviour that the maintainers acknowledge rather than a documented contract.

### Gaps
- No Microsoft Learn text states that Administrators-group SSH sessions are elevated; the maintainers' comments on #1652 could not be read (proxy), so the exact wording of their answer is unknown. Verify on a host with `whoami /groups | findstr /i "High Mandatory"` inside an SSH session.

Proposed replacement for lines 23–35, using the module's own mechanism (a local Task Scheduler job running as SYSTEM) and waiting for it so `run-remote.sh` still gets a synchronous result:
  ```powershell
  Log 'Windows Update (PSWindowsUpdate module)'
  try {
    if (-not (Get-Module -ListAvailable -Name PSWindowsUpdate)) {
      Install-PackageProvider -Name NuGet -MinimumVersion 2.8.5.201 -Force | Out-Null
      Set-PSRepository -Name PSGallery -InstallationPolicy Trusted
      Install-Module -Name PSWindowsUpdate -Force -Scope AllUsers
    }
    Import-Module PSWindowsUpdate
    # Listing works in any session; downloading/installing does not from an SSH (network-logon) session:
    # the WUA API refuses CreateUpdateDownloader/CreateUpdateInstaller with E_ACCESSDENIED. The module's
    # answer is Invoke-WUJob: a Task Scheduler job that runs the install locally as SYSTEM.
    Get-WindowsUpdate -AcceptAll -IgnoreReboot | Out-Host                       # list only
    $wuLog = 'C:\ProgramData\trimurti-wu.log'
    Invoke-WUJob -ComputerName $env:COMPUTERNAME -RunNow -Confirm:$false -Force `
      -Script "ipmo PSWindowsUpdate; Get-WindowsUpdate -AcceptAll -Install -IgnoreReboot *>&1 | Out-File '$wuLog'" | Out-Null
    Start-Sleep 10
    while ((Get-ScheduledTask -TaskName 'PSWindowsUpdate' -ErrorAction SilentlyContinue).State -eq 'Running') { Start-Sleep 20 }
    if (Test-Path $wuLog) { Get-Content $wuLog | Out-Host }
    $reboot = [bool](Get-WURebootStatus -Silent)
  } catch {
    Write-Warning "PSWindowsUpdate failed: $($_.Exception.Message). Use Settings > Windows Update on this machine instead."
  }
  ```
  (`-Script` is a string per the help text; `TaskName` defaults to `PSWindowsUpdate`; the log path avoids `$Env:TEMP`, which resolves to `C:\Windows\Temp` under SYSTEM. If the script is run from a local elevated console instead of SSH, the direct call works, but the job path works in both cases.)
- Install steps: the kit's NuGet-provider + `Set-PSRepository ... Trusted` + `Install-Module -Force -Scope AllUsers` sequence matches what Microsoft's own docs use; the module README only requires `Install-Module PSWindowsUpdate` plus the TLS 1.2 line the kit already sets. No change. Microsoft's example adds `-MicrosoftUpdate` (other Microsoft products); optional.
- `Get-WURebootStatus -Silent` is fine. Add a third registry check, guarded against the known false positives: `if ((Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Session Manager' -Name PendingFileRenameOperations -ErrorAction SilentlyContinue).PendingFileRenameOperations) { $reboot = $true }`.
- Update the header comment "Run elevated (an SSH session as an administrator already is)" to add "Windows Update itself runs through a scheduled task because the WUA API rejects SSH (network-logon) callers".

### Gaps

  function Find-Winget {
